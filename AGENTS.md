# Technical decisions

- Vite `build.target` must be the single string `'es2020'`, never a multi-engine list like `['es2020', 'safari14']`: esbuild 0.27.2's transform API falsely reports destructuring as unsupported when the target list contains multiple engines (fixed by Grafana et al. in esbuild 0.27.5+). If esbuild is ever upgraded past 0.27.2, a list can be restored if needed.
- Keep the `es2020` floor (Safari 14+): many members use older iPhones, so do not raise the build target above it.
- The read-aloud Bible voice (non-narrated translations) runs only in the cloud (`bible-tts` edge function → Lovable AI speech, WAV → MP3 in `aiVoice/encoder.worker.ts`); the ~290 MB on-device model froze phones and was removed. Offline listening = chapters kept on the device (heard, or saved per book in Listen offline). Don't call it "AI voice" anywhere members can see.
- Next/previous chapter logic lives in `services/audioBible/nextChapter.ts` (fuzzy book-name matching, tested); the player prefetches the next chapter's playable link so auto-advance starts with no awaits (phones block delayed background play).
- Call earpiece/loudspeaker (`lib/calls/callEngine.ts`, "Earpiece or loudspeaker"): voice calls start on the earpiece. iPhone (Safari 18.4+): `setSinkId` to the "Receiver" output, which WebKit turns into a phone-call audio session (no DefaultToSpeaker, VoiceChat mode). Safari allows `setSinkId` only within 5 s of a tap, so it runs straight after Call/Answer, on a fixed set of `<audio>` elements made at call start (`lib/calls/callAudio.ts`). Don't go back to per-person audio elements made later, or the call falls back to the loudspeaker. Android (Chrome): switch the microphone to "Headset earpiece" / "Speakerphone".
- Study notes ("Notes from" in Bible → Study notes, `services/studyNotesService.ts`): Christian notes only. Tyndale Open Study Notes (default) and the classic Christian commentaries named in `KNOWN` come from the Free Use Bible API (anything else it lists is hidden). Matthew Henry's Concise Commentary and the Geneva Bible notes, both public domain, are served by the app from `public/study-notes/{id}/{BOOK}/{chapter}.json`; rebuild them with `scripts/make-study-notes.py` (sources in its header). They're cached once opened, not precached. The Life Application Study Bible isn't offered (Tyndale's copyright), not even as a link to Tecarta.
- Installing: `lib/install.ts` (device detection, Android's install offer caught at startup) + `components/install/` (Home card, step-by-step guide). `public/install/ThePowerHouse.mobileconfig` is an iPhone profile that adds the app to the Home Screen; remake it with `scripts/make-install-profile.py`.
- Church Space (one app for many churches): everything specific to a church — name, logo, colours, links, contacts, campuses, giving details, live times, choir branches, Home banners and which parts of the app it uses — lives in `src/config/church.ts` (the server functions' copy: `supabase/functions/_shared/church.ts`). Never hard-code a church's details anywhere else. Parts a church can switch off are tagged `feature` in `src/data/appDirectory.ts`, and their pages are guarded by `src/components/FeatureGate.tsx`. index.html (`%CHURCH_…%`) and manifest.json are made from the profile at build time (`src/config/brandFiles.ts` + the `churchBrand` plugin in vite.config.ts), so editing the profile restarts the dev server.
- Many churches, one database: church-owned tables have `church_id`, and a restrictive "Only this church" rule uses `current_church_id()` (the `x-church-id` header if you're a member, else your first church, else The Power House). `src/lib/churchSpace.ts` (imported first in main.tsx) picks the church: The Power House on its own address; on `PLATFORM.hosts` (churchspaceapp.vercel.app, space.localhost for testing) the church chosen on the phone, or "Find your church". The header goes on database requests only, never server functions (their CORS rejects it). The accent colour is Tailwind `blue`, pointed at `--brand-*` variables so each church can pick its own. Database tests: pglite scripts (see the step 1–3 migrations, 20261028*).
- Vercel builds: `vercel.json` turns off builds for `claude/**` branches (no preview copies of work in progress). Every build is kept as a full copy (~77 MB, mostly `public/audio` and `App_Intro_1.mp4`), and the free plan's Deployment Storage cap is 10 GB.
- Notes (`pages/BibleNotesPage.tsx`): a folders-first home (All notes, Favourites, Not in a folder, My folders, Recent); a list opens as `?view=all|favourites|unfiled|<folderId>`, so Back returns to the home. Folder colours are `bible_note_folders.color` (migration 20261030100000; the ids and classes are in `components/notes/folderColors.ts`). A folder with no saved colour takes the next one in folder order, which is what the migration saves. The service retries without `color` if that column isn't there yet.
- Church admin (Me → Admin, `is_admin` = an active `administrator` or `pastor` role in `user_roles`): The Power House has one, Ayodeji Augustine (dejiaugustine@gmail.com). Migration 20261030120000 switched off everyone else's admin roles there. Chat "Admin" (`group_admins`) is separate and only means anything in groups: a one-to-one chat's info is a contact card (`GroupInfoSheet`, `isPrivateChat`).
- National choir passcode: the database checks it (`choir_passcodes`, hashed; `choir_unlock` for the unlock button; `choir_can_edit` restrictive rules on every choir table, migration 20261030140000). After unlocking, the app sends it as `x-choir-key` on database requests (`lib/choirKey.ts`). Never put a passcode in the app's code. Branch choirs stay open to everyone with no account. The Contribution Tracker (location "National") uses the same passcode, and church admins can always edit. Newcomer survey answers (`service_feedback`): anyone can send them, and only church admins can read them.
- Follow-up team passcode (Teams → Team follow-up, `team_follow_ups`: visitors' names, phone numbers and notes): it works like the choir passcode, with `follow_up_passcodes` (hashed), `follow_up_unlock`, and `follow_up_access` restrictive rules on reading and changing, migration 20261030160000. The app sends it as `x-follow-up-key` (`lib/followUpKey.ts`, shared code in `lib/passcodeKey.ts`). Church admins can always open it. The backing-tracks files stay open to everyone on purpose: the choir adds and deletes them without accounts.
- Social Circle, live (`lib/socialLive.ts`): `friendships` is in the realtime publication (migration 20261031090000), and the app listens to your own friendships the whole time it's open (NotificationContext). Deletes can't be filtered and carry only the id, so a delete is acted on only if the id is in your circle. Any change refetches the circle once (`refreshCircle`) and gives it to every screen (`circle:changed`): the Friends and Requests lists, the Requests badge, and Discover's buttons. Elsewhere in the app it shows a banner, with the same key as the push so they never double up. The Social page also catches up when the app comes back on screen, comes back online or reconnects, and every 30 s while it's open, for Home Screen apps whose connection sleeps.
- Live everywhere: a screen that shows shared data uses `useLiveRefresh(tables, refresh)` (`hooks/useLiveRefresh.ts`). It refreshes on realtime changes to those tables (each must be in the realtime publication: see migration 20261031120000 for the list), on coming back on screen, online or reconnected, and every 60 s while on screen. Refreshes must be quiet (no spinner, no error pop-up). Busy tables like `app_activity` aren't published, so those pass no tables and just poll. Any new screen with shared data should use it.
- Live service on YouTube (`services/youtube.ts`, one shared check for Home and Watch): `live_services` marked live by an admin comes first. Watch/Home have a "We're live" switch (`LiveControls`); with no link it plays the channel's live stream (`embed/live_stream?channel=`). Then the `youtube-live` edge function checks, using the YouTube API (the uploads list plus live details, 2 units, cached 60 s) when `YOUTUBE_API_KEY` is set, otherwise the channel's /live page. `api/youtube-live.js` (Vercel) is the backup. The app checks every 20 s around service times or while live, and every 60 s otherwise. Detection works any day, not only at the usual service times.
- Notes offline (`lib/offlineNotes.ts`): every change is written to the phone first, as a draft (`note_draft_<user>_<id>`), and only then sent. The draft is removed only once that exact version is saved. A new note gets its id on the phone (`newNoteId`, and it's upserted, so sending it twice makes no duplicate). The lists lay drafts over the account's notes (`withDrafts`), marked `pending` with "Not synced yet". Drafts sync on start, on online, when the app is back on screen, and every 30 s while any wait (OfflineSync). If a note was changed on another device since the draft's `base`, the phone's version is saved as "… (copy)": nothing is ever thrown away. Never compare database times as strings: use `timeOf`, because the database writes microseconds.
- Bible highlights offline (`services/bibleHighlightsService.ts`): a copy of the account's highlights is kept on the phone (`bible_highlights_cache_v1_<user>`). It's refreshed on every online read, and in full on start and on coming back (OfflineSync `refreshCopy`), so every chapter shows its highlights with no connection. Changes made offline are queued (`bible_highlights_queue_v1`), shown on top, and sent in order: on start, on online, on coming back on screen, and every 30 s while any wait. Requests give up after 15 s and queue instead. Highlights are live across devices (migration 20261031150000).
- Editing messages (like WhatsApp): the sender can change a message's text, or a photo's or video's caption, for 15 minutes after sending (long-press → Edit; the text goes back in the message box with an "Edit message" banner, and whatever was being typed comes back after). Everyone sees "Edited" beside the time (`chat_messages.edited_at`). The database enforces it (migration 20261102090000, trigger `chat_message_guard`): only the text changes, only within 15 minutes (plus 30 s grace), never for calls, deleted messages or a photo's file, and a message keeps its chat, sender and time. `edited_at` is set only by the trigger. Edits reach open chats instantly (`message-edited` signal), from the database feed (UPDATE), and after sleep (`getRecentEdits`: only the last 16 minutes can change); chat lists reload their latest line. `canEditMessage` in `chatUtils.ts` decides when Edit is offered.
- Chats like WhatsApp (migration 20261102120000): swipe a message right to reply (`MessageBubble` pointer swipe on the bubble, `touch-pan-y`, 56 px; also Reply in the menu). `chat_messages.reply_to_id` (same chat only: trigger `chat_message_reply_check`) shows the original quoted above the reply; tapping it scrolls to it and flashes it, loading older messages if needed (`jumpTo`, `getMessagesBetween`), and quotes not loaded are fetched (`getMessagesByIds`). Forward sends a copy to up to 5 chats (`ForwardSheet`, `forwarded` = "Forwarded" label). Star (`chat_starred_messages`, each person's own; Starred messages in the chat's info), Pin (`chat_pins`, one per chat, any member, live via realtime + `pin` signal; banner under the header), Delete for me (`chat_hidden_messages`), Search in a chat (chat info → Search, `searchMessages`), and Info on my messages (read by / not read yet, from read marks). The long-press menu: reactions, then Reply · Forward · Copy · Star · Pin, then Edit, Info, Delete for me, Delete for everyone. `chat_message_guard` also keeps `reply_to_id` and `forwarded` unchanged on edit. Sending falls back to a plain message if the reply/forward columns aren't there yet. The chat's section has `min-w-0` and banner text `w-0` so a long one-line quote can't widen the page.
- End-to-end encrypted chats (`lib/chatCrypto.ts`, migration 20261102150000): each phone/browser makes an ECDH P-256 key pair (private key non-exportable, IndexedDB `ph-chat-keys`; public key in `chat_devices`). Each chat has AES-256-GCM keys, sealed separately for every member device in `chat_keys` (secret = SHA-256 of the two devices' ECDH bits + context). Messages are stored as `::e2e::1:<keyId>:<iv>:<ct>` (bound to the chat id); photos are encrypted files (`.bin`) whose key travels in the message (`#e2e=key.iv.type`, opened by `SecureImg`/`useOpenedImage`). Encrypt in `GroupChatService.sendMessage`/`editMessage`/`importMessages`; every way messages arrive goes through `readable()` (lists, realtime, signals, search, starred, quotes). Call records (`::call::`) stay plain. A device without a chat's key shows "🔒 Waiting for this message" (`locked`, `cipher`) until another member's device seals it the key: `ChatKeySync` (mounted in App) registers the device and runs `shareAllKeys` on start, when back on screen, and when someone adds a device (realtime on `chat_devices`); keys sealed for this device fire `KEYS_ARRIVED`. Removing a member makes the next message use a new key (`membersChanged`); new members are sealed the existing keys (they see history, as before). Encryption only switches on once the tables exist (`e2eReady`). Notifications: `send-push` sends "🔒 New message" plus the scrambled text in `data.e2e`; `public/push-sw.js` opens it with the key in IndexedDB (`chatkey:<chat>:<key>`). Each chat starts with WhatsApp's cream notice ("🔒 Messages and calls are end-to-end encrypted. Only people in this chat can read, listen to, or share them. Learn more"; `SolidLock`, and `EncryptionInfo` explains it). Search opens the latest 2,000 messages on the phone (plus a server search of old plain ones). Videos aren't encrypted files yet (their link is inside the encrypted message). Never send a message's text to the server or a function in the clear.
- Importing a WhatsApp chat (chat info → Import WhatsApp chat, `WhatsAppImport.tsx`, `lib/whatsappImport.ts`): reads the export (.txt, or .zip with `_chat.txt` + photos via fflate) on the phone, iPhone and Android formats, 12/24-hour, day/month order from a value over 12 or the phone's own date format ("Swap day and month" if wrong). The member picks which name is them; others are matched to members when they can be. Rows are saved by the importer with `imported_from` (WhatsApp name), `imported_as` (matched member, checked by the insert trigger), the original `created_at`, encrypted like any message; photos are uploaded (encrypted); videos, voice notes and documents become a "(not imported)" note. Realtime ignores imported rows (no banners, no list jumps); one `imported` signal reloads open chats and lists. Unread counts leave imported rows out. Bubbles show "Imported".
- Bottom bar: on every page on phones (only the first-time /intro has none), including open chats (the message box sits above it) and the newcomer survey. `BottomNavigation` measures how much of the screen it takes (`lib/bottomNav.ts`: `--bottom-nav-h`, `useBottomNavHeight`), and every layer ends above it so it stays visible and tappable: windows (`ui/dialog`, `ui/alert-dialog`: backdrop ends at the bar, centred in the space above it, max height `100dvh - bar`; a window's own near-full max height subtracts the bar too), sheets on every side and drawers (`ui/sheet`, `ui/drawer`: bottom offset, max height `92dvh - bar`), and the app's own full-screen layers (note editor, a plan's day reader, New group, Search, the photo viewer). The bar takes taps while a window is open (`pointer-events-auto`): a tap closes the window, or the page under it changes (Search closes when the page does). For bottom padding inside these, use `var(--sheet-safe-bottom,env(safe-area-inset-bottom))` (it's 0 above the bar). `useKeyboardSafeHeight` pads only by the part of the iPhone keyboard below the view. While Android's keyboard shrinks the page (`interactive-widget=resizes-content`), the bar steps aside (`useKeyboardLiftsPage`) so it doesn't sit on the keyboard; the iPhone keyboard just covers it. Any new full-screen layer must end at `bottom: var(--bottom-nav-h)`. Only calls and the welcome tour cover it, on purpose. The note editor saves when it unmounts (a tab tapped mid-sentence).
